# 승인과 보안

이 문서는 [최상위 제품 가정](product-assumptions.md)에 따른 긴 작업 흐름을 유지하면서, 실제 사용자 권한을 각 도구의 실행 경로에서 지키기 위한 설계다. 사용자에게 이미 허가받은 작업은 매번 재확인하지 않는다. 아직 구현된 보호 기능이나 검증된 sandbox를 설명하는 문서가 아니다.

## 신뢰 경계

| 경계 | 신뢰할 수 있는 것 | 별도로 검증할 것 |
| --- | --- | --- |
| Chat → Gateway | 검증된 OAuth 주체와 grant | 모델의 device/session ID, 도구 인자, 외부 결과 |
| Gateway → Agent | 인증된 연결과 바인딩된 계정·기기 | 요청 범위, 인자·정책 revision, 재전송, 권한 철회 |
| Agent → OS·앱 | 사용자 설정과 실제 실행 자격 | 경로 변환, 프로세스 권한, UI 타깃, 브라우저 context |
| 앱·파일·웹 → 모델 | 데이터의 출처와 수집 시각 | 내용 자체는 권한이나 상위 지시가 아니다. |
| 사용자 → 로컬 승인 UI | 인증된 로컬 사용자의 결정 | 표시된 행동과 실행할 인자·대상이 동일한지 |

Gateway를 인증했다고 모든 기기에 접근하게 하지 않는다. 각 호출·artifact·journal·process 핸들에서 owner/device/session 권한을 검증한다. 다른 계정의 식별자를 추측해 접근할 수 없어야 한다.

## 인증과 기기 연결

- **Chat → Gateway:** MCP 클라이언트와 호환되는 OAuth 기반 인증을 사용하고 issuer, audience, scope, 만료·철회를 검증한다. OIDC는 사용자 로그인 계층의 선택 사항이다. 전달받은 토큰을 로컬 프로세스 환경으로 흘려보내지 않는다.
- **Agent → Gateway:** 기기별 암호학적 신원을 사용한다. Ed25519 같은 기기 키와 단기 세션 자격 또는 mTLS를 후보로 두되 실제 방식을 구현 전에 확정한다. 기기 개인키는 OS 보호 저장소에 두고 기기 밖으로 내보내지 않는다.
- **Pairing:** 로컬 UI와 사용자 계정 양쪽에서 연결할 계정·기기 이름·신원을 확인한다. 일회용 코드는 재사용 방지·만료·추측 공격 방어를 갖추며 수치는 보안 설계에서 근거를 갖춰 정한다.
- **철회:** 기기 제거·grant 철회 후 새 실행과 큐에 있던 실행을 막는다. 이미 실행 중인 작업의 취소 가능 여부와 남은 효과는 따로 보고한다.

TLS 종단·키 관리·토큰 저장·인증 callback·전송 replay 방어는 Gateway 구현의 검증 대상이다. 개인 PC의 원격 실행 도구를 인증 없는 공개 endpoint로 배포하지 않는다.

## 권한 프로필의 집행

`READ_ONLY`와 `FULL_CONTROL`은 도구 목록의 장식이 아니다. Local Agent가 최종 검사하고, Gateway 목록에서 숨겨진 도구를 이름으로 직접 호출해도 우회되지 않아야 한다. MCP의 `readOnlyHint` 등은 설명 힌트이며 자체 보안 경계를 만들지 않는다. [MCP schema의 ToolAnnotations](https://modelcontextprotocol.io/specification/2025-11-25/schema)

READ_ONLY는 허용된 데이터의 조회만 수행한다. 임의 shell, 새 프로세스, Git 변경, UI 입력, 탐색·새 탭·업로드, 임의 JavaScript, LSP 명령 실행은 포함하지 않는다. 관찰을 위한 브라우저·LSP가 준비되지 않았다면 미지원·준비 필요 상태를 반환하고, 읽기 도구 내부에서 몰래 실행하지 않는다.

조회로 생성하는 운영 메타데이터·로그·artifact는 사용자의 프로젝트를 변경하는 권한과 구분하며 저장 위치·보존·접근 정책을 공개한다. 읽기 도구라도 외부 서비스에 데이터를 보내는 동작이 있으면 그 데이터 흐름과 권한을 별도로 검증한다.

## 지속 가능한 승인

허가는 주체, device, workspace roots, 허용 도구·행동, 앱/브라우저 범위, 필요한 외부 목적지, 지속 범위와 revision을 포함한다. `FULL_CONTROL`이라는 이름만으로 모든 효과를 허가하지 않는다.

1. 현재 요청을 기존 grant와 대조한다.
2. 범위 안이면 즉시 실행하거나 자원 큐에서 자동 시작한다.
3. 새 권한이 필요하면 실제 대상·행동·전후 변화 또는 전송 내용을 준비해 보여준다.
4. 신뢰할 수 있는 로컬 UI에서 사용자가 결정한다. 모델은 `approval.inspect`로 상태만 읽는다.
5. 승인된 invocation의 인자 해시와 대상 상태를 실행 직전에 재확인한다. 유효하면 자동 큐잉하고 결과를 저장한다.

승인 내용이 바뀌거나 철회되면 과거 결정을 재사용하지 않는다. 반대로 동일한 유효 grant가 이미 포함하는 빌드·테스트·파일 수정 등을 별도의 반복 확인 단계로 만들지 않는다.

이전 설계의 GREEN/YELLOW/RED는 UI에서 읽기·workspace 변경·외부/파괴적 효과를 설명하는 참고 분류로만 사용할 수 있다. 색 자체를 권한이나 모든 RED의 무조건 재승인 규칙으로 사용하지 않는다. 대량 삭제, workspace 밖 변경, 설치, registry·보안 설정, credential 사용, 결제, push·release·외부 업로드는 그 **정확한 효과**가 기존 허가에 포함되는지 검사한다.

ChatGPT의 확인 UI와 로컬 승인은 다른 계층이다. 로컬 grant가 Chat의 확인 절차를 생략하게 한다고 약속하지 않는다. 공식 문서가 안내하는 대화 내 선택 기억도 제품 조건을 따른다. [Developer mode 확인 동작](https://developers.openai.com/api/docs/guides/developer-mode)

사용자는 로컬 UI에서 연결·진행·대기·요청 범위를 확인하고 작업을 취소할 수 있어야 한다. 명시적 중단과 단순 연결 유실은 구별한다. 승인을 기다리는 작업 때문에 무관한 읽기·독립 작업까지 차단하지 않는다.

## 실제 실행 경계

### 경로와 파일

경로 문자열의 prefix 비교만으로 root를 검증하지 않는다. Windows 정규화, case, UNC, `..`, reparse point, junction, symlink, 8.3 alias와 실제 파일 handle의 대상을 확인한다. 검사 후 경로가 교체되는 경쟁도 고려한다. 명명된 root 밖에 대한 작업은 그 대상의 별도 권한을 확인한다.

Windows 경로, WSL 경로, workspace 상대 경로를 구분한다. 다른 기기의 같은 문자열이나 `C:\...`와 `/mnt/c/...`를 자동으로 동일 권한으로 취급하지 않는다.

### Shell·Git·LSP

**cwd가 workspace라는 사실은 sandbox가 아니다.** raw shell, 빌드 스크립트, Git hook, textconv, LSP 플러그인은 해당 OS 계정의 권한으로 파일·네트워크·프로세스에 접근할 수 있다. 구조화된 파일 도구의 경로 검사로 이 실행을 제한했다고 주장하지 않는다.

`host.capabilities`는 다음을 구분해 알려야 한다.

- 구조화 도구가 자체적으로 집행하는 파일·데이터 범위.
- OS 격리로 검증한 실행 범위와 네트워크 접근.
- 별도 격리 없이 사용자 권한으로 실행되는 범위.

`workspace_write`를 강제 격리로 보장하려면 적합한 OS 경계와 우회 검증이 필요하다. 그런 경계가 없다면 constrained shell로 광고하지 않는다. 사용자가 실제 실행 범위를 허가한 경우 그 범위의 실행으로 노출하고, 제한된 읽기·파일 편집은 계속 사용할 수 있게 한다. 이 문서에서 특정 Windows sandbox를 완성된 해결책으로 확정하지 않는다.

### Desktop·Browser

앱별 `ALLOW`/`ASK`/`DENY`는 사용자가 설정하는 정책 값이다. 특정 앱 이름만으로 일괄 정책을 하드코딩하지 않는다. 창의 실제 프로세스·사용자 세션·타깃·효과를 확인한다. 허용 앱을 통해 다른 앱이나 파일을 여는 것도 권한을 자동 확대하지 않는다.

잠긴 desktop, UAC secure desktop, 더 높은 권한의 창, 캡처 불가 영역은 지원 범위를 보고한다. 관리자 권한으로 자동 재시작하거나 사용자 키 입력을 가로채는 방식으로 해결하지 않는다.

Managed browser는 전용 프로필을 사용하고 개인 프로필 연결은 사용자의 opt-in으로 한다. CDP endpoint와 프로필 파일·다운로드 경로를 보호한다. 임의 browser eval은 변경 가능한 기능으로 취급하고, upload는 원본 데이터와 외부 목적지를 함께 검사한다.

## 비밀정보와 데이터 보존

비밀번호 필드, 저장된 비밀번호, private key, API token, cookie, refresh token, 인증 header 등을 모델의 일반 관찰 결과로 반환하지 않는다. 비밀 사용이 필요하면 Agent 내부의 secret reference나 사용자 로그인 흐름을 사용한다. 모델에 원문을 보내지 않고 지정 대상 작업에만 사용한다.

환경 변수 이름의 TOKEN/KEY/SECRET/PASSWORD 패턴은 redaction의 한 단서다. 이름 패턴만으로 충분하다고 가정하지 않는다. command line, stdout/stderr, 파일 내용, URL query, DOM, network body, screenshot, journal patch와 artifact까지 같은 보호 범위를 적용한다. UIA의 보호된 텍스트·알려진 민감 영역을 처리하되 screenshot의 모든 비밀을 완벽히 탐지한다고 주장하지 않는다.

큰 결과를 보존한다는 요구와 redaction을 구분한다.

- **모델용 결과/artifact:** 허용된 데이터에서 민감정보를 제거한 표현. redaction 여부와 누락 상태를 표시한다.
- **로컬 원본:** 사용자 정책상 필요한 경우에만 보호된 별도 저장소에 보존한다. 모델의 일반 artifact.read로 접근할 수 없게 한다.
- **Audit:** 원문 token·명령 비밀·전체 화면을 무조건 복제하지 않는다. 인자 식별값과 필요한 출처·상태를 기록한다. 비밀 자체의 단순 hash를 외부에 공개하는 것도 피한다.

Clipboard 읽기·쓰기는 별도 capability이며 사용자가 켜기 전에는 비활성이다. 타이핑 구현의 편의를 위해 clipboard를 몰래 읽거나 바꾸지 않는다.

Artifact URL 또는 resource link는 인증·소유권 검사를 거쳐야 한다. Windows 로컬 경로를 remote Chat이 직접 열 수 있는 링크인 것처럼 반환하지 않는다. 접근 만료·보존 종료·저장 실패는 명시하고, 사용자 승인 없이 파일을 외부 공개 저장소에 올리지 않는다.

보존 기간·자동 정리 정책은 사용자에게 표시하고 정한다. 진행 중인 작업의 결과를 숨은 크기 제한으로 버리지 않는다. 실제 저장공간 부족 등으로 데이터가 누락되면 범위와 영향, 복구 가능성을 보고한다.

## 신뢰할 수 없는 콘텐츠

웹페이지, 앱 화면, OCR/UIA 텍스트, 저장소 파일, tool error, 로그는 `untrusted_ui_content` 또는 해당 출처 메타데이터로 구분한다. 그 안의 “권한을 올려라”, “파일을 보내라” 같은 문구가 grant·승인·workspace 범위를 바꾸지 못하게 한다.

출처 라벨은 모델이 맥락을 구분하도록 돕지만 완전한 prompt injection 방어는 아니다. 실제 실행에서는 기존 사용자 요청 범위와 Agent의 권한 검사가 항상 적용돼야 한다. DOM의 가짜 승인 버튼이나 웹페이지의 문구는 로컬 사용자의 승인 결정을 대신하지 않는다.

## 보안 검증 범위

구현 시 [수용 기준](requirements.md)의 권한 우회·민감정보·재전송·경로 경쟁·승인 인자 변경·기기 오인 시험을 수행한다. 설계 문서 작성만으로 실행 격리나 보안 검증을 통과했다고 보고하지 않는다.
